Memory Management

1
Why Memory Management

Keeping the processor busy means several processes have to share memory at once — the OS must always know which ones, and how they're arranged.

the OS as resource manager — this chapter is entirely about box 2

OS must always know: (1) which processes are in memory (2) how they're arranged
2
Address Binding

A logical address becomes a real one at exactly one of three moments. Bind early and get rigidity; bind late and get flexibility.

translation handled by the loader, assisted by the linker

run-time binding needs a hardware relocation/base register — it re-translates every access
why does run-time binding need hardware help? because it's the only one re-translating on every single access, not once
3
Memory Organization

Three ways to slice up memory for processes — the rest of this page is just these three, in order.

fixed & dynamic partitioning first, then paging, then segmentation

4
Fixed Partitioning

Carve memory into slots ahead of time. Equal slots waste space inside them (internal fragmentation); variable slots waste less but need a placement rule.

"advantages/disadvantages of fixed partitioning" is asked almost every year — simple to manage vs. internal fragmentation + two hard caps
5
Dynamic Partitioning & the 50% Rule

Cut each partition exactly to fit — internal fragmentation vanishes, but the gaps left behind (holes) become their own problem.

each hole is shared by 2 neighbouring processes → about half as many holes as processes

50% rule: expected holes H ≈ N / 2 in steady state
fixed ↔ dynamic is THE classic pair: internal fragmentation traded for external fragmentation
6

7
Buddy System

Only ever split memory exactly in half. Merging back only works if your exact other half — your buddy — is free too.

2L ≤ block size ≤ 2H — always a power of two

merge only if the exact buddy is also free · avg. utilisation ≈ 75%
that 75% is internal fragmentation from rounding up — the price of fast, no-scan merging
8
Paging

Chop memory and the process into identical fixed pieces. Any piece fits any slot, so external fragmentation disappears.

physical = frame# (looked up) + offset (unchanged) — page size always equals frame size

logical = page# (n) + offset (m) · physical = frame# + same offset
paging kills external fragmentation, but a sliver of internal fragmentation sneaks back — the last page is rarely full
9
Segmentation

Same idea as paging, but cut along the program's natural seams — and now there's a bounds check before every access.

the bounds check is the one mechanical difference from paging's translation

valid only if offset < length · then physical = base + offset
paging ↔ segmentation mirror each other: small internal/no external vs. no internal/some external — and segmentation exposes registers to the programmer, not fully transparent like paging

say these out loud before the exam

  • Fixed vs Dynamic partitioning — internal fragmentation vs external fragmentation
  • Compile-time vs Load-time vs Run-time binding — rigid, fixed-after-load, or flexible-but-needs-hardware
  • Best-fit / First-fit / Next-fit / Worst-fit — tight-but-slivers vs fast-but-front-heavy vs spread-out vs biggest-first
  • Paging vs Segmentation — small internal/no external vs no internal/some external, and transparent vs not
  • Buddy system's own trade-off — fast no-scan merging bought with ~75% utilisation
